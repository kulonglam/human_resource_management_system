# Deploy checklist — FCA HRMIS

Use this guide to sync **staging** and **production** on Render after pushing code changes.

## 1. Sync the Render blueprint

1. Open [Render Dashboard](https://dashboard.render.com) → **Blueprints**
2. Select the HRMIS blueprint linked to this repo
3. Click **Manual Sync** (or push to `main` if auto-deploy is enabled)
4. Confirm two web services and two databases are created:
   - `human-resource-management-system` (production)
   - `human-resource-management-system-staging` (staging)
   - `avvento-hrmis-db` / `avvento-hrmis-db-staging`

### Build command (required)

The React SPA must be built during deploy (`frontend/dist`). If you see:

`React frontend is not built. Run: cd frontend && npm install && npm run build`

your Render service is missing the frontend build step.

**Blueprint / `render.yaml` services** use:

```bash
bash scripts/render-build.sh
```

**Manually created services** — open Render → your web service → **Settings** → **Build Command** and set:

```bash
bash scripts/render-build.sh && python manage.py migrate --noinput
```

(or keep `migrate` in **Pre-Deploy Command** as in `render.yaml` instead of the build step).

### Start command (required)

The start command only launches the web server. It does **not** build the frontend or run migrations.

**Blueprint / `render.yaml` services** use:

```bash
gunicorn avvento_hrmis.wsgi:application --bind 0.0.0.0:$PORT
```

**Manually created services** — Render → your web service → **Settings** → **Start Command**:

```bash
gunicorn avvento_hrmis.wsgi:application --bind 0.0.0.0:$PORT
```

Do **not** use `python manage.py runserver` in production, and do not put `npm run build` or `migrate` in the start command.

### Pre-deploy command (recommended)

If you are not using the blueprint, set **Pre-Deploy Command** to:

```bash
python manage.py migrate --noinput && python manage.py bootstrap_admin && python manage.py seed_workflows
```

### Quick reference (manual Render service)

| Setting | Command |
|---------|---------|
| **Build** | `bash scripts/render-build.sh` |
| **Pre-Deploy** | `python manage.py migrate --noinput && python manage.py bootstrap_admin && python manage.py seed_workflows` |
| **Start** | `gunicorn avvento_hrmis.wsgi:application --bind 0.0.0.0:$PORT --workers 2 --threads 2 --timeout 120` |
| **Health check path** | `/api/v1/health/` |

### Redis and scalability (production blueprint)

The blueprint provisions a Render Key Value instance (`hrmis-redis`) and wires `REDIS_URL` to web, worker, and ops-alert services via the `hrmis-shared-redis` env group.

| Component | Production default |
|-----------|-------------------|
| Web / staging plan | `starter` |
| Postgres plan | `starter` |
| Worker plan | `starter` |
| Key Value plan | `starter` (`noeviction` — safe for django-q queues) |
| Gunicorn | `--workers 2 --threads 2 --timeout 120` |

When `REDIS_URL` is set:
- Django cache uses **Redis** (shared SLO counters, MFA tokens, login lockout, alert cooldowns)
- django-q uses **Redis** as the broker instead of the app database

Local development works without Redis (LocMem cache + ORM-backed django-q). To test Redis locally:

```bash
docker run --name hrmis-redis -p 6379:6379 -d redis:7
set REDIS_URL=redis://127.0.0.1:6379/0
python manage.py qcluster
```

Health check reports Redis status: `/api/v1/health/` includes `redis: ok | unavailable | not_configured`.

## 4. Staging → production workflow

1. Push changes to `main`
2. Staging deploys first (same branch) — smoke test:
   - Login + MFA setup
   - Create leave / expense / appraisal
   - Check audit log at `/audit-logs`
   - Confirm emails arrive (if SMTP configured)
3. Production auto-deploys from the same push (or promote manually)
4. Re-check health endpoint and admin MFA on production

## 5. Scheduled tasks (cron)

The blueprint defines **Render Cron Jobs** and a **django-q worker** for production:

| Job | Schedule (UTC) | Command |
|-----|----------------|---------|
| `hrmis-daily-scheduled-reports` | 07:00 daily | `python manage.py run_scheduled_tasks --skip-backup` |
| `hrmis-monthly-tasks` | 06:00 on the 1st of each month | `python manage.py run_scheduled_tasks --skip-backup` |
| `hrmis-weekly-backup` | 05:00 Sundays (UTC) | `python manage.py backup_database && python manage.py verify_backup` |
| `hrmis-ops-alerts` | every 10 minutes | `python manage.py check_ops_alerts` |
| `hrmis-staging-monthly-dr` | 08:00 on the 1st of each month | `python manage.py run_monthly_dr_checks` |

After blueprint sync, open **hrmis-weekly-backup** → Environment and set the same `FIELD_ENCRYPTION_KEY` (and preferred `BACKUP_ENCRYPTION_KEY`) used by the web service. Optional: `BACKUP_S3_BUCKET` + AWS credentials for offsite upload. These are declared with `sync: false` so Render prompts for them without committing secrets.
| `hrmis-annual-holidays` | 07:00 on 1 January | `python manage.py seed_uganda_holidays` |
| `hrmis-qcluster` | continuous worker | `python manage.py qcluster` |

Monthly tasks run leave accrual, document expiry reminders, **data retention enforcement**, due scheduled report emails, and the shared ops alert check. **Weekly backup** creates an encrypted dump, verifies decrypt + integrity, and optionally uploads to S3. **Staging monthly DR** runs backup + verify + isolated restore drill and records compliance evidence (see `DISASTER_RECOVERY.md`).

Retention purge also runs on the daily cron via `run_scheduled_tasks` (idempotent). Preview or run manually:

```powershell
python manage.py apply_retention_policies --dry-run
python manage.py apply_retention_policies
# Skip during a scheduled run if investigating an incident:
python manage.py run_scheduled_tasks --skip-backup --skip-retention
```

Compliance / risk docs: [INCIDENT_RESPONSE.md](INCIDENT_RESPONSE.md) · [RISK_REGISTER.md](RISK_REGISTER.md) · [ENV.md](ENV.md)

### Backup / restore drill

Backups use **streaming Fernet encryption** (chunked, memory-safe). When `ENCRYPT_BACKUPS=True`:

- **PostgreSQL:** `pg_dump -Fc` (custom format) stdout is encrypted directly — only `.dump.enc` under `backups/` (no plaintext).
- **SQLite:** a snapshot is written to a temp file, encrypted, then the temp file is **securely overwritten and deleted**.
- Restore/verify decrypt to temp paths that are wiped the same way.

Legacy plain `.sql` / single-blob `.enc` files still restore.

```powershell
# Create encrypted backup (SQLite dev or pg_dump -Fc in prod)
python manage.py backup_database

# Verify without touching the live database
python manage.py verify_backup
python manage.py verify_backup --path backups\postgres_20260101_120000.dump.enc

# Restore (destructive — requires --force)
# Postgres custom dumps use: pg_restore --clean --if-exists --no-owner --no-acl
python manage.py restore_database backups\postgres_YYYYMMDD.dump.enc --force

# SQLite
python manage.py restore_database backups\sqlite_YYYYMMDD.sqlite3.enc --force
```

**Clean restore notes (PostgreSQL):**

1. Put the app in maintenance (scale to 0 / block traffic).
2. Prefer restoring onto a **staging** database first and run `verify_backup` + smoke tests.
3. Production restore uses `pg_restore --clean --if-exists` by default (drops & recreates objects). Pass `--no-clean` only for rare additive restores.
4. For a full database replacement (empty DB), recreate the empty database on the host, then restore — do not mix schemas from two eras without `--clean`.
5. After restore: `python manage.py migrate --check`, hit `/api/v1/health/`, smoke login + payroll.
6. Document wall-clock restore time for RTO evidence.

**Local retention:** after each successful `backup_database`, old `sqlite_*` / `postgres_*` files are pruned (`BACKUP_RETENTION_COUNT` + `BACKUP_RETENTION_DAYS`). Manual prune:

```powershell
python manage.py prune_backups --dry-run
python manage.py prune_backups
```

Configure S3 object lifecycle in AWS for offsite retention (app does not delete S3 objects).
Set on production:

| Variable | Purpose |
|----------|---------|
| `ENCRYPT_BACKUPS` | `True` (default when `DEBUG=False`) |
| `BACKUP_ENCRYPTION_KEY` | **Preferred** key for backup file encryption (distinct from PII). Generate separately from `FIELD_ENCRYPTION_KEY`. |
| `BACKUP_ENCRYPTION_KEY_PREVIOUS` | Comma-separated prior backup keys for rotation |
| `REQUIRE_BACKUP_ENCRYPTION_KEY` | `True` to refuse encrypting backups without a dedicated key |
| `FIELD_ENCRYPTION_KEY` | PII field encryption; also decrypts older backups if backup key unset |
| `BACKUP_S3_BUCKET` | Optional offsite copy after local encrypt. When set, upload **must** succeed or `backup_database` exits with error (fail closed). |
| `BACKUP_S3_SSE` | `AES256` (default) or `aws:kms` |
| `BACKUP_S3_SSE_KMS_KEY_ID` | KMS key when using `aws:kms` |
| `BACKUP_RETENTION_COUNT` | Keep newest N local backups (default `14`; `0` disables) |
| `BACKUP_RETENTION_DAYS` | Delete local backups older than D days (default `30`; `0` disables) |

Run backup + verify in one job:

```powershell
python manage.py run_scheduled_tasks --verify-backup
```

Register django-q schedules once:

```powershell
python manage.py setup_enterprise_schedules
python manage.py seed_compliance_evidence
```

After blueprint sync, confirm cron and worker services appear in the Render dashboard and have `DATABASE_URL` linked to `avvento-hrmis-db`.

### Ops / SLO / SCIM

| Endpoint | Purpose |
|----------|---------|
| `/api/v1/ops/status/` | Queue counts, backups, runbooks, **alert history / cooldown** |
| `/api/v1/ops/slos/` | Availability & latency for current hour |
| `/api/v1/api-changelog/` | Versioned deprecation policy |
| `/api/v1/scim/v2/Users` | SCIM user list/provision |
| `/settings/ops` | Admin Operations Center UI (includes active breaches + recent emissions) |

Active alerting:
- `check_ops_alerts` evaluates the same health and SLO logic used by `/api/v1/health/` and `/api/v1/ops/slos/`.
- On breach, it creates in-app admin notifications, emails `HR_NOTIFY_EMAIL`, and emits a Sentry message if `SENTRY_DSN` is configured.
- Alerts are deduplicated for `OPS_ALERT_COOLDOWN_MINUTES` (default `30`) to avoid noise.

## 7. Local pre-deploy checks

```powershell
pip install -r requirements.txt
python manage.py check
python manage.py test api.tests
cd frontend ; npm ci ; npm run test ; npm run build
```

CI runs backend `api.tests` on **SQLite and PostgreSQL** (GitHub Actions matrix), frontend Vitest + production build, and Playwright E2E (auth, leave, approvals, payroll, MFA). See `.github/workflows/ci.yml`.

OpenAPI contract: `api/tests/fixtures/openapi_schema.yaml` is compared in CI. After intentional API changes, refresh with:

```powershell
$env:UPDATE_OPENAPI_SNAPSHOT='1'
python manage.py test api.tests.test_api_contract.OpenAPISchemaTests.test_openapi_schema_matches_snapshot
```

Playwright E2E: `cd frontend ; npx playwright install ; npm run e2e` (with app + API running).
